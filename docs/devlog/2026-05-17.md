# Devlog - 2026-05-17

## Goal

Move OnLive 音 Live Mode from a Gradio-style demo toward a custom React/FastAPI web application, while keeping Csound reliable as the core real-time audio engine.

## Work completed

- Built the Live Mode web app around React, React Router, and a FastAPI backend.
- Recreated Csound audio device selection from `csound --devices` so input/output selectors use real `adc` and `dac` ports.
- Added start, stop, refresh, and device apply controls for the live Csound process.
- Added OSC-based effect controls for pitch shift, ring mod, blur, flanger, and EQ.
- Added Csound output telemetry on a separate UDP port and streamed it through the Live WebSocket.
- Replaced the fake waveform animation with real output waveform and EQ analyzer panels.
- Reworked the page layout so the effects rack is the main focus and waveform/EQ visuals act as secondary monitoring.
- Collapsed the verbose Csound console behind an Expand/Hide control.
- Fixed Stop behavior after failed Csound launches so the UI can clean up failed states.
- Added device channel-count handling so Csound launches with matching `--nchnls_i` and `--nchnls` values.

## Technical details

- Backend Live Mode is centered on a single Csound subprocess manager that owns process start/stop, device selection, OSC parameter updates, recent logs, and status snapshots.
- Device parsing now reads Csound input/output metadata and channel counts from Core Audio device listings.
- Csound control OSC remains on port `7777`; output telemetry uses port `7778` to avoid mixing control messages with visualization data.
- Telemetry is sampled from the final processed output before `outs`, so waveform and EQ visualization reflect the real live signal after all effects.
- The frontend receives status, logs, and telemetry over the existing Live WebSocket and draws the waveform/EQ panels with canvas.
- The console no longer renders long Csound logs by default; it shows a short summary unless expanded.

## Issues / Bugs

- Default `adc0/dac0` routing could fail because `Studio Display Speakers` exposes 8 output channels while Csound was previously launched with a fixed 2-channel configuration.
- Stop was disabled after Csound failed because the process had already exited, leaving the UI unable to clear the failed state.
- Old Csound log output stayed visible, making previous `1 errors in performance` messages look like current failures.
- Vite sometimes served stale frontend code until the dev server was restarted.
- Browser automation occasionally timed out while clicking in the in-app browser, so API and DOM checks were also used for verification.

## Solutions / Decisions

- Launch Csound with selected-device channel counts using `--nchnls_i` and `--nchnls`.
- Allow Stop in Csound failure states and clear telemetry/log state during cleanup.
- Clear the Csound console at the beginning of each new run so logs describe only the current session.
- Keep waveform/EQ visualization as compact supporting monitors, with the effects controls as the primary Live Mode surface.
- Keep the full Csound console available, but collapsed by default to reduce visual clutter.

## Next steps

- Test Live Mode with the intended real microphone/interface and output device, not only BlackHole routing.
- Add clearer device compatibility hints when a selected input/output pair is likely to fail.
- Persist the last successful input/output selection between sessions.
- Continue measuring practical audio latency for each effect with real hardware.
- Review Docker deployment after the local Live Mode flow is stable.

## Notes / Reflection

Today clarified that Csound must remain the source of truth for both sound and signal visualization. The UI should support live performance first: effects need to be prominent, while waveform, EQ, logs, and diagnostics should help without overwhelming the page.
