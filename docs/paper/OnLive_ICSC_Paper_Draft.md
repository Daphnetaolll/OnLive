## Abstract

This paper presents OnLive 音, a browser-based real-time audio performance system that uses Csound as its sound engine and a custom React interface as its performance console. The project was developed from an earlier Gradio-based demonstration into a front-end/back-end architecture that separates interface design, process control, sample management, and digital signal processing. OnLive 音 is designed for musicians, creative coders, and performers who want to reshape live microphone, instrument, or sample-pad audio into memory-like sonic textures without working inside a conventional digital audio workstation. The current system includes real Csound input/output device discovery, exclusive Live and Sample modes, eight sample pads with one-shot and loop playback, optional BPM synchronization, real-time OSC parameter control, output waveform and EQ telemetry, master EQ, master volume, final-bus limiting, and Docker-oriented deployment support. The paper describes the artistic motivation, system architecture, DSP chain, interaction design, validation process, and future work for OnLive 音 as a performance-oriented Csound web instrument.

**Keywords:** Csound, Web Audio Interface, Live Performance, FastAPI, React, OSC, Sample Pads, Real-Time Audio Processing, Interactive Music System

## 1 Context: Designing a Web Instrument for Memory-Like Audio

OnLive 音 began as an audio tool for transforming sound into expressive, memory-like distortion. The artistic premise is that remembered sound rarely returns with perfect fidelity: it blurs, delays, detunes, folds into noise, and becomes emotionally colored by time. Instead of treating distortion as only a technical effect, OnLive 音 treats distortion as a performable metaphor for memory.

The project has two workflows. The original Studio Mode is a Gradio-based offline renderer that accepts uploaded audio files and produces processed WAV or MP3 files through Python DSP routines. The newer Live Mode is the primary system described in this paper. It is a custom web application built with React, React Router, FastAPI, and Csound. Live Mode lets a performer process a microphone, instrument, virtual audio device, or uploaded sample pads through a shared real-time Csound effects chain.

The key design goal is to preserve Csound as the source of truth for audio while using the browser for control and visual feedback. The browser does not record or play the audio stream directly. Instead, Csound owns the audio route from selected input device to selected output device. The web interface sends control values and displays telemetry generated by the final Csound output. This separation avoids browser audio permission and routing issues while still allowing a highly customized performance interface.

## 2 Related Work and Reference Paper Structure

The reference papers supplied for this project share a practical ICSC-style structure: an artistic or accessibility context, a system description, an explanation of control mappings, implementation details, observations or evaluation, future work, and references. Liu's face-tracking CsoundUnity system maps facial movements to Csound parameters and sample triggers, emphasizing alternative access to musical expression. Kobayashi's Laser Synth paper focuses on playability and expressive control in VR by mapping object distance and rotation to pitch, filter, and XY-pad parameters. Zhong's interactive composition paper describes how Unity mechanics, C# scripts, trigger systems, and Csound channels can combine into an interactive audiovisual composition.

OnLive 音 shares the same broader concern with these works: Csound becomes more performable when paired with an interface layer that maps human action into musical control. However, OnLive 音 differs from the Unity-based examples by using a browser and local FastAPI server instead of a game engine. The central interaction is not face tracking, VR object manipulation, or collision detection, but a performance console with device routing, sample pads, effect controls, master controls, and real-time signal visualization. The design question is therefore: how can Csound be embedded into a web-controlled live performance workflow while maintaining reliable audio routing and musician-friendly control?

## 3 System Overview

OnLive 音 Live Mode is organized as a four-layer system:

1. **React interface:** renders the performance console, device selectors, transport controls, sample pads, effect panels, master controls, waveform visualization, EQ analyzer, and Csound console.
2. **FastAPI back end:** owns the local Csound process, exposes REST endpoints, receives telemetry, and streams state to the browser through WebSocket.
3. **OSC control layer:** sends validated performance parameters from the back end to Csound on port 7777.
4. **Csound DSP engine:** performs live input processing, sample playback, effects, EQ, limiting, output routing, and telemetry generation.

The overall architecture can be summarized as:

```text
React UI + React Router
        |
        | REST + WebSocket
        v
FastAPI Backend
        |
        | owns one Csound subprocess
        v
CsoundEngine
        |
        | OSC controls on 127.0.0.1:7777
        v
Csound DSP
        |
        | final processed audio
        v
Audio Output Device

Csound telemetry on 127.0.0.1:7778
        |
        v
FastAPI TelemetryReceiver
        |
        | /api/live/events
        v
Output Waveform + EQ Analyzer
```

## 4 User Workflow

The Live Mode workflow begins with device selection. The interface queries `csound --devices`, parses available `adc` input devices and `dac` output devices, and presents them in the browser. The user applies a selected input/output route, then starts Csound. Csound is launched with the selected audio devices and a small buffer configuration intended for live use.

The performer can then adjust the following live effects:

- **Pitch Shifter:** on/off, dry/wet, semitone shift from -12 to +12.
- **Ring Mod:** on/off and dry/wet.
- **Blur:** on/off, memory length, and dry/wet.
- **Flanger:** on/off, dry/wet, and LFO rate.
- **ATS Cross:** a spectral layer adapted from ATS analysis files, controlled by on/off, dry/wet, morph, and speed.
- **Master EQ:** low, mid, and high gain controls.
- **Master Volume:** final user-facing level control before limiting.
- **Limiter:** threshold, ceiling, attack, and release for final-bus protection.

Sample Mode provides a second workflow. Instead of using a microphone input, the user enables Sample Mode and uploads up to eight samples. Pads can be triggered as one-shots or loops. Loop mode can use the original sample speed or synchronize playback to a global BPM value. When an uploaded sample includes a detectable tempo, the interface can suggest using that BPM for the session.

## 5 Implementation

### 5.1 Front-End Interface

The front end is written in React with React Router. The main route is `/live`, implemented in `frontend/src/routes/Live.tsx`. The Live page is responsible for fetching devices, status, logs, sample metadata, and telemetry. It keeps local state for selected input/output devices, current Csound status, parameter values, sample slots, errors, and tempo suggestions.

The interface is componentized around performance responsibilities:

- `DeviceSelect.tsx` renders adc/dac selectors.
- `TransportControls.tsx` renders apply, start, stop, refresh, and sample mode controls.
- `EffectPanel.tsx` renders each live effect and its variant selector.
- `SamplePadSection.tsx` and `SamplePad.tsx` render the eight-pad sample player.
- `SignalScope.tsx` renders output waveform and EQ analyzer canvases.
- `MasterEqPanel.tsx` renders master EQ, volume, and limiter controls.
- `ConsoleLog.tsx` exposes Csound logs behind an expandable panel.

Effect definitions are centralized in `frontend/src/lib/liveControls.ts`. This file maps UI controls to OSC-style paths such as `/ol/pitch/wet`, `/ol/ats/morph`, and `/ol/limiter/threshold`. This mapping makes the UI extensible: new Csound effect variants can be added by updating the Csound branch, the back-end OSC validation table, and the front-end control definition.

### 5.2 FastAPI Back End

The back end is a FastAPI application. Its live API routes are located in `backend/app/api/routes_live.py`, while process ownership is handled by `backend/app/services/csound_engine.py`. The back end exposes endpoints for device discovery, starting and stopping Csound, selecting devices, updating parameters, uploading samples, changing sample mode, triggering pads, reading logs, and receiving live WebSocket updates.

The `CsoundEngine` class is intentionally a single owner of the Csound subprocess. It validates parameter ranges, keeps a recent log buffer, sends OSC messages, and restarts Csound when device routing changes. The Docker backend is configured to run one Uvicorn worker so only one process owns the live audio engine at a time.

The current REST interface includes:

- `GET /api/live/devices`
- `PATCH /api/live/devices/selection`
- `POST /api/live/start`
- `POST /api/live/stop`
- `GET /api/live/status`
- `PATCH /api/live/params`
- `PATCH /api/live/params/batch`
- `GET /api/live/logs`
- `GET /api/live/samples`
- `POST /api/live/samples/mode`
- `PUT /api/live/samples/{slot}`
- `PATCH /api/live/samples/{slot}`
- `DELETE /api/live/samples/{slot}`
- `POST /api/live/samples/{slot}/trigger`
- `WS /api/live/events`

The WebSocket endpoint streams status, recent logs, and telemetry snapshots. It runs at approximately 30 frames per second for telemetry, while full status and logs are sent at a lower interval.

### 5.3 Csound DSP Chain

The current Csound file is `backend/app/dsp/on_live.csd`. It defines k-rate channels for mode, transport, sample loop state, effect parameters, EQ, volume, and limiter controls. A dedicated OSC listener instrument receives parameter messages and updates channels with `chnset`.

The main Csound instrument performs the following signal path:

```text
Live input or Sample Mode source
        |
DC block + high-pass safety filtering
        |
Pitch Shifter
        |
Ring Mod
        |
Blur
        |
Flanger
        |
ATS Cross spectral layer
        |
Low/Mid/High EQ
        |
Low-end feedback guard + soft saturation
        |
Master Volume
        |
Final Limiter
        |
Telemetry probes
        |
outs
```

Sample Mode is exclusive. When sample mode is enabled, the back end launches Csound with `--nchnls_i=0`, and the Csound microphone path becomes silence. This prevents microphone input and sample playback from entering the effects chain at the same time. Sample voices write into a shared sample bus, which then enters the same effects chain as live audio.

The effects are designed as performance controls rather than offline render presets. The pitch shifter uses phase-vocoder analysis and resynthesis. The ring modulator uses sine oscillators. Blur combines delay memory with spectral resynthesis. Flanger uses modulated delay taps. ATS Cross is adapted from an analysis-file-based Csound effect and behaves as a live/sample-gated spectral layer rather than a direct `ain -> aout` processor, because the original opcode relies on pre-analyzed ATS files.

### 5.4 Output Telemetry

The browser visualizations are not synthetic animations. Csound generates lightweight telemetry from the final processed output after effects, EQ, master volume, and limiting. This telemetry is sent through OSC on port 7778 and received by `TelemetryReceiver` in the FastAPI process.

The telemetry stream includes:

- waveform min/max envelope data,
- RMS level,
- peak level,
- clip state,
- a 16-band spectrum approximation.

The receiver stores the latest telemetry in a thread-safe snapshot. If Csound is stopped or the telemetry becomes stale, the back end returns an idle baseline. This prevents the UI from showing fake motion when there is no real audio signal.

### 5.5 Sample Mode and Tempo

The sample system is implemented in `backend/app/services/sample_bank.py`. It provides a fixed eight-slot sample bank. Uploaded files are validated, converted with Pydub to 44.1 kHz stereo WAV, and stored as `pad_00.wav` through `pad_07.wav`. Metadata is stored in JSON and includes name, duration, detected BPM, confidence, playback mode, loop bars, and gain.

Tempo detection is implemented without large analysis dependencies. `tempo_detection.py` downmixes the audio, computes frame energies, derives an onset envelope, and searches for the strongest autocorrelation lag between 40 and 240 BPM. The estimate is confidence-tagged and used only as a suggestion. The user can accept the detected tempo or keep samples at their original speed.

Loop mode supports 1 to 8 bar loop lengths. When tempo sync is enabled, Csound computes loop duration from the BPM and bar count, then adjusts playback rate so the sample fits the chosen musical length. When tempo sync is disabled, loops play at original audio speed.

### 5.6 Deployment

OnLive 音 includes Docker support for packaging the React front end, FastAPI back end, Csound, FFmpeg, and Nginx. The frontend Dockerfile builds the React application and serves it through Nginx, proxying `/api/` requests and WebSocket upgrades to the back end. The backend Dockerfile installs Csound, FFmpeg, and Python dependencies.

On Linux, audio devices can be exposed through an additional Docker Compose override for `/dev/snd`. On macOS, Docker Desktop usually cannot access Core Audio devices in the same direct way, so the recommended development configuration is to run the back end locally for real audio access and use Docker for packaging and API/frontend testing.

## 6 Performance Design

The performance design follows three principles.

First, control should be immediate. Toggling an effect sends the current slider values as a grouped state snapshot, so a performer does not need to move a slider after enabling an effect. This reduces the difference between visual state and audio state.

Second, live input and sample input should be clearly separated. A Sample Mode button explicitly switches the source from microphone input to sample pads. This avoids hidden routing ambiguity and reduces feedback risk during testing.

Third, the interface should show what Csound is actually doing. The waveform and EQ analyzer are tied to Csound's final output telemetry, not to browser-side fake animation. This makes the visuals useful for debugging and for performance feedback.

## 7 Validation

The current project was reviewed across front-end, back-end, DSP, sample, telemetry, and deployment code. The reviewed implementation includes approximately 6330 lines across core Python, TypeScript, CSS, and Csound files.

Functional validation for this draft included:

- TypeScript and Vite production build: passed.
- Python back-end compilation with `compileall`: passed.
- Csound syntax check for `on_live.csd`: passed with 0 performance errors.
- API health endpoint verified Csound binary discovery and CSD path existence.
- Local front-end and back-end dev servers verified on ports 5175 and 8000.

The current validation is primarily technical rather than formal user testing. It confirms that the architecture is coherent, the code compiles, and the Csound orchestra parses. A future study should evaluate latency, learnability, musical expressiveness, accessibility, and performer confidence with real users.

## 8 Discussion

OnLive 音 demonstrates one approach to making Csound more approachable without hiding its strengths. The web interface is visually custom and musician-oriented, while Csound still handles audio input, DSP, sample playback, and output routing. This division is important because browser audio routing can be inconsistent across systems, especially when external audio interfaces and virtual routing tools are involved.

The system also reveals several tradeoffs. Using a local FastAPI process gives strong control over Csound and device routing, but it means the application is not a purely static website. It must be run as a local audio tool. The telemetry design avoids streaming full audio data to the browser, reducing complexity and permission issues, but it provides an approximation of spectrum rather than a full FFT analyzer. The ATS Cross effect adds a distinctive spectral character, but because the original ATScross opcode is based on analysis files, it has been adapted as a gated spectral layer instead of a conventional live effect.

From a performance perspective, Sample Mode is one of the most important additions. It lets the performer test live effects without opening a microphone, which reduces acoustic feedback and makes the system more playful. It also brings OnLive 音 closer to hybrid live performance tools such as drum pads, loopers, and Ableton-style clip playback, while keeping the effects chain unified.

## 9 Future Work

Future development can proceed in five directions.

First, OnLive 音 should support more same-category effect variants. The existing variant selector structure already anticipates alternate pitch, ring, blur, and flanger branches. Future additions could include granular pitch shifting, spectral freeze, tape-style wobble, convolution-based spaces, or more controlled ATS-based spectral transformations.

Second, the sample pad system can become more performance-ready. Possible additions include pad colors, choke groups, quantized launch, visual beat phase, per-pad gain, per-pad mute, and clip trimming.

Third, telemetry can be expanded. A higher-resolution analyzer, limiter gain-reduction meter, and per-effect activity indicators would make the system more useful for both sound design and debugging.

Fourth, the project should undergo structured user testing. Inspired by the reference papers' focus on observations and performer feedback, future evaluation should include musicians, non-DAW users, and creative coders. Useful research questions include how quickly users understand the routing model, whether the controls feel expressive, whether Sample Mode helps testing, and whether the output visuals improve confidence.

Fifth, deployment can be refined. Local macOS audio access remains best handled outside Docker, but Linux deployment could be strengthened with ALSA/PipeWire documentation and device presets. A packaged desktop wrapper may also make the local web architecture easier for performers to launch.

## 10 Conclusion

OnLive 音 is a Csound-based web performance instrument designed around memory-like audio transformation. Its contribution is not a single DSP algorithm, but a complete interaction architecture: Csound performs the sound, FastAPI owns process control and telemetry, React provides a custom performance interface, and sample pads make the effects playable without a live microphone. By separating audio ownership from browser control, OnLive 音 keeps the reliability of Csound while gaining the flexibility of modern web interface design. The project is positioned as both a creative tool and a platform for future research into browser-controlled Csound performance systems.
